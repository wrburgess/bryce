# Testing Rules

**Applies to:** The test suite
**Deep doc:** `docs/rules/testing-postmortems.md` (Tier 2 — deferred; read on demand when a trigger fires)

> Tier-1 Lean Core ([ADR 0004](../docs/adr/0004-two-tier-rules-layer-progressive-context.md)): always-resident invariants. Keep this file lean — push heavy, subsystem-specific case studies down to the deep doc. These are business-neutral, stack-neutral starters; **extend per host** — concrete stack-named examples live in the matching **Stack Overlay** (e.g. `ai-config-rails`), vendored alongside the baseline.

## Patterns

- **Test behavior and side effects**, not that the code merely runs: assert content, database state, redirects, and enqueued work.
- **Cover the sad paths**: invalid input, `nil`, duplicates, and boundary values — that is where regressions hide.
- **Build the test infrastructure the scenario needs** (helpers, shared setup, data builders, HTTP record/replay) rather than declaring a thing untestable. That is part of the work, not a reason to skip it.
- **Self-review before "done":** for each test ask, "if this passed but the feature were broken, would I know?"
- **Evaluate LLM-driven behavior with task-specific evals**, not only example-based asserts: when a feature's output is *graded* rather than exact (a rubric, an LLM-as-judge, a golden-set score), treat the eval as a first-class test that runs in CI alongside the suite, with an explicit pass threshold. *(Extend per host.)*
- **Construct the environment a test claims to cover.** When behavior depends on where the code runs — path shape, working directory, platform separator — build each shape inside the test rather than relying on the one the suite happens to run in; an environment-dependent assertion is green on one machine and red on another. *(Provenance: issue #139 / PR #147; host case study: `docs/rules/testing-postmortems.md`. Extend per host.)*
- **Enforce the offline-test invariant fail-closed, not by convention.** Block non-loopback egress in the harness itself (`test/support/network-guard.ts`, wired in `vitest.config.ts` `setupFiles`), and both throw **and** record each attempt — because a comment declaring "tests never hit the network" enforces nothing, and a provider's fail-open catch can swallow the throw but not the record. A real external call belongs in the `*.live.test.ts` tier (`npm run test:live`). *(Provenance: issue #25; host case study: `docs/rules/testing-postmortems.md`. Extend per host.)*
- **Enforce coverage floors against the report the run produced, not against a declaration.** Per-file minimums live in a manifest a post-run diagnostic reads (`scripts/coverage-floors.ts`, chained into `npm run test:coverage`); a floored path *missing* from the summary fails exactly like one below its number, because a config-declared threshold is compared only against the files its glob matched and one matching zero files passes silently. *(Provenance: issue #28; host case study: `docs/rules/testing-postmortems.md`. Extend per host.)*

## Anti-Patterns

- **Never build tests on schema-coupled static test data** — because it drifts from the schema and obscures intent; construct each case's data with programmatic builders instead. *(Extend per host.)*
- **Never assert only a status code / `success`** — because a broken feature can still return 200; assert the content, side effects, and redirect. *(Extend per host.)*
- **Never insert wall-clock waits in a test** (a real-time sleep) — because it is flaky and slow; control the clock — freeze or advance time — instead. *(Extend per host.)*
- **Never claim something "can't be tested" without first attempting it** with the host's stack — because most "untestable" cases have a documented tool (headless browser, HTTP record/replay). *(Extend per host.)*
- **Never ship LLM-driven behavior guarded only by deterministic asserts** — because a model or prompt change can regress output quality while every equality check still passes; add a task-specific eval with a graded threshold. *(Extend per host.)*
- **Never prove a cross-process concurrency invariant with a second in-process connection alone** — because a same-process handle shares the runtime's locks, caches, and descriptors and can pass while the real race survives; spawn a genuine second process, close your own handle so the spawn is the sole participant, and assert it is actually refused. *(Provenance: issue #67 / PR #80; host case study: `docs/rules/testing-postmortems.md`. Extend per host.)*
- **Never test a gate's logic without also pinning what invokes it** — because a checker nothing calls is not a gate: every rule and sad path can pass at full strength while a one-line edit to the npm script or the CI step removes the only call site. Assert the invocation against the real manifest and workflow file. *(Provenance: issue #28 / PR #138; host case study: `docs/rules/testing-postmortems.md`. Extend per host.)*
- **Never scope a fixture's copy filter by substring-matching an absolute path** — because the excluded segment can occur in the copy *root* as well as under it, so the filter rejects every source and the empty fixture surfaces far from its cause; compare the excluded directory by absolute equality (or relative to the copy root), and make the copier throw when the result is unusable. *(Provenance: issue #139 / PR #147; host case study: `docs/rules/testing-postmortems.md`. Extend per host.)*
- **Never test a new limit with an input that an EARLIER validation already rejects** — because the test passes for the wrong reason and would keep passing if the limit were deleted: an over-long *segment* used to exercise an *aggregate*-length bound is refused by the per-segment rule first, so the aggregate rule never runs. Build an input valid under every **other** rule, assert the **specific** error the limit raises, and confirm by deleting the limit that the test fails. *(Provenance: issue #140 / PR #150; extend per host.)*
- **Never assert a bound against a proxy constant instead of the property the bound exists to give** — because the proxy can hold while the real constraint is violated: "16 tokens x 64 characters < 4096" says nothing about the 998-octet header line the limit was added to respect, and the worst legal input still rendered ~2,094 characters. Derive the assertion from the actual constraint, and bound the aggregate the consumer sees, not the parts it is built from. *(Provenance: issue #140 / PR #150; extend per host.)*
- **Never construct a default/real provider client in a default-suite test, or reach a live service** — because a forgotten fake egresses (flakiness, rate limits, real email, unintended production contact) and a fail-open catch can hide it behind a green pass; inject a fake transport, or use the `*.live.test.ts` tier via `npm run test:live`. *(Provenance: issue #25; host case study: `docs/rules/testing-postmortems.md`. Extend per host.)*
- **Never assert "no findings" on an input that would also yield none if the guard were broken** — because the case passes in both worlds and reads as coverage while pinning nothing; size the benign input so the specific defect you fear would push it over the line, then break the guard and confirm the test fails. *(Provenance: issue #152 / PR #157; extend per host.)*
